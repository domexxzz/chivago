# คำถามก่อนเชื่อมต่อ ChivarGo × Sentiara AI

**อ้างอิง:** เอกสารแนวคิด "Chivar Go × Sentiara AI — ระบบบริหารเกาะสีชังอัจฉริยะ" ฉบับวันที่ 17 พฤศจิกายน 2569 (12 หัวข้อ)
**จัดทำรายการคำถาม:** 18 พฤศจิกายน 2569
**บันทึกคำตอบจากฝั่ง Sentiara:** 18 พฤศจิกายน 2569

**สถานะ:** ข้อ 1, 2 และ 8 ซึ่งเป็นตัวตัดสิน **มีคำตอบแล้ว** — การออกแบบฝั่ง ChivarGo ปลดล็อกแล้ว ส่วนหมวด 5 และ 6 (สิทธิ์ กฎหมาย เงิน) ยังไม่มีคำตอบเลย เพราะฝั่งโค้ดตอบไม่ได้ ต้องให้ผู้บริหารและเจ้าของกล้องตอบ

> **สิ่งที่ยังไม่ได้ตรวจสอบ:** คำตอบในเอกสารนี้คือคำตอบที่ฝั่ง Sentiara ส่งมา บันทึกไว้ตามที่ได้รับ ฝั่ง ChivarGo ยังไม่ได้เห็นโค้ด ยังไม่ได้ทดสอบยิงเข้ามาจริง และยังไม่ได้ตรวจไฟล์ที่เขาอ้างถึง (`sentiara/services/incident_bridge.py` และอื่น ๆ) ว่ามีจริง เขาระบุเองว่า **ยังไม่ได้ deploy ขึ้นเครื่องจริงเครื่องไหน และยังไม่เคยยิงมาที่ ChivarGo ตัวจริง**

**สัญลักษณ์:** ✅ ตอบแล้ว ใช้ออกแบบได้ · ⚠️ ตอบแล้วแต่ยังไม่ยืนยัน หรือตัวเลขไม่ใช่ของเกาะ · ❌ ยังไม่มีคำตอบ

## หมวด 1 การเชื่อมต่อ

> ถ้าข้อ 1 ตอบว่าไม่ได้ โครงการนี้จบ — **ตอบว่าได้**

**1. Sentiara ส่งเหตุออกจากระบบตัวเองได้ไหม — ทาง webhook, ทาง API หรือดูได้เฉพาะในหน้าจอของตัวเอง** ✅

- เหตุผลที่ถาม: ฝั่ง ChivarGo ตอนนี้ไม่มี route ไหนใน `apps/api/src/server.ts` รับ event จากระบบภายนอกได้เลยสักอัน ต้องสร้างใหม่ทั้งหมด และสร้างได้ต่อเมื่อรู้ว่าอีกฝั่งส่งอะไรมา
- **คำตอบ:** ได้ ทาง webhook — `POST` ไปที่ URL ที่ฝั่ง ChivarGo กำหนด (`CHIVARGO_INCIDENT_URL`) ก่อนหน้านี้ส่งออกได้แค่ Telegram ตัวส่งปิดเป็นค่าเริ่มต้น เปิดเมื่อตั้ง URL และ secret ครบ เขาระบุว่าสร้างตัวส่งเสร็จในวันเดียวกับที่ได้รับคำถามนี้

**2. ขอตัวอย่าง payload จริงหนึ่งก้อนเป็น JSON ไม่ใช่คำอธิบายเป็นข้อความ** ✅

- **คำตอบ:** ได้ก้อนจริงจากการยิงผ่าน HTTP ในเครื่องเขา (ตัวรับจำลองตรวจลายเซ็นผ่าน)

```json
{
  "incidentId": "sen-7c58fb58af74f42875fc780a",
  "source": "sentiara",
  "detectorVersion": "frigate-car",
  "kind": "vehicle_obstruction",
  "observedAt": "2026-11-18T14:02:11+07:00",
  "camera": { "id": "pier_01", "owner": "เทศบาล", "lat": 13.15, "lng": 100.81 },
  "location": { "lat": 13.15, "lng": 100.81, "accuracy": "camera_only" },
  "confidence": 0.8,
  "provenance": "ai_estimate",
  "verified": false,
  "description": "กล้อง pier_01 ตรวจพบรถยนต์ · รถจอดกีดขวาง",
  "evidence": [{ "kind": "image", "ref": "https://<base>/v1/incidents/evidence/sen-…?exp=…&sig=…",
                 "expiresAt": "2026-11-19T14:02:11+07:00" }]
}
```

- ต่างจากร่างในเอกสารแนวคิด §4.1 สองจุด: เพิ่ม `incidentId` (ตอบข้อ 5) และ `evidence[].kind` เป็น `image` ไม่ใช่ `image_pair` เพราะวันนี้ส่งภาพเดียวจาก Frigate
- `description` เป็นประโยคแม่แบบ คำบรรยายจาก VLM (Sentiara Eye) ยังไม่ได้ต่อเข้า

**3. ยืนยันตัวตนอย่างไร — API key, HMAC signature หรือ mTLS** ✅

- เหตุผลที่ถาม: ChivarGo มีแต่ token ของมือถือผู้ใช้ (`device_keys` ผูกกับ `users`) ไม่มี credential สำหรับระบบคุยกับระบบ ต้องทำใหม่
- **คำตอบ:** HMAC-SHA256 ด้วย shared secret (ต้อง ≥ 24 ตัว สั้นกว่านี้ระบบเขาถือว่าไม่ได้ตั้ง) ไม่ใช้ mTLS เพราะเครื่องหน้างานอยู่หลัง NAT/Tailscale

```
X-Sentiara-Timestamp: <unix วินาที>
X-Sentiara-Signature: sha256=<hex ของ HMAC(secret, "<timestamp>." + body ดิบ)>
Idempotency-Key:      <incidentId>
```

- **ข้อกำหนดกับฝั่งเรา:** ต้องปฏิเสธ timestamp ที่ห่างจากนาฬิกาเกิน 5 นาที (กัน replay) และเทียบลายเซ็นแบบ constant-time

**4. ถ้าฝั่ง ChivarGo ล่มหรือรับไม่ทัน Sentiara ส่งซ้ำไหม เก็บคิวไว้นานเท่าไหร่** ✅

- **คำตอบ:** ส่งซ้ำ คิวอยู่ใน SQLite บนเครื่องหน้างาน (`data/incident_outbox.db`)

```
2xx / 409                 = ส่งแล้ว (409 = ปลายทางมีเหตุนี้อยู่แล้ว)
เน็ตล่ม / 5xx / 408 / 429 = ลองใหม่ ถอยห่าง 30s → 1m → 2m → 5m → 15m → 30m → 1h
4xx อื่น                  = ถูกปฏิเสธ ไม่ลองซ้ำ (บันทึกรหัสไว้)
ค้างเกิน 24 ชม.            = หมดอายุ ไม่ส่ง แต่ยังนับให้เห็นใน /v1/incidents/status
```

**5. มี event id ที่คงที่ต่อเหตุหนึ่งเหตุไหม เพื่อไม่ให้เหตุเดียวถูกบันทึกซ้ำสองครั้ง** ⚠️

- **คำตอบ:** มี `incidentId = "sen-" + sha256(กล้อง | kind | ช่วงเวลา 10 นาที)[:24]` event จาก Frigate หลายครั้งของรถคันเดียวใน 10 นาทีนับเป็นเหตุเดียว ส่งซ้ำกี่รอบ id ก็เดิม
- ⚠️ เขาเตือนเองว่า **รถจอดค้างข้ามรอยต่อช่วงเวลาจะได้ 2 id** ฝั่งรับควรรวมด้วยกล้อง + kind อีกชั้นถ้าต้องการ

**6. ส่งสถานะตามมาทีหลังได้ไหม เช่น เหตุนี้ยกเลิก หรือเหตุนี้เป็นการแจ้งผิด** ⚠️

- **คำตอบ:** ทางกลับมีแล้ว ทางไปยังไม่มี
  - **ChivarGo → Sentiara:** `POST /v1/incidents/outcome` ค่าที่รับคือ `confirmed | false_alarm | duplicate | unresolved` ต้องลงลายเซ็นแบบเดียวกันด้วยหัว `X-ChivarGo-Timestamp` / `X-ChivarGo-Signature` ผลไปลง `data/incident_outcomes.jsonl` เพื่อเป็นชุดสอนรอบหน้า ผลที่เซ็นก่อนทับผลที่เซ็นทีหลังไม่ได้ (ตอบ 409)
  - **Sentiara → ChivarGo "เหตุนี้ยกเลิก":** ยังไม่มี เหตุผลของเขาคือ AI ไม่ควรเป็นฝ่ายยกเลิกเหตุที่คนยังไม่ได้ดู ผลตัดสินควรมาจากเจ้าหน้าที่ฝั่ง ChivarGo

## หมวด 2 ภาพและคลิป

> ฐานข้อมูลทั้งแพลตฟอร์มของ ChivarGo อยู่ใน Durable Object ก้อนเดียว เพดาน 10 GB เมื่อเต็มจะเกิด `SQLITE_FULL` ซึ่งหยุดการเขียนทั้งระบบ ไม่ใช่แค่ตารางที่โต คำตอบของหมวดนี้จึงเป็นตัวกำหนดวิธีออกแบบที่เก็บ
>
> **ผลของหมวดนี้:** ภาพอยู่ฝั่ง Sentiara ส่งมาแค่ลิงก์ — ความเสี่ยง 10 GB จากภาพกล้องหมดไป เงื่อนไข ข. ได้ตามที่ต้องการ

**7. ส่งภาพนิ่งหรือคลิป ขนาดต่อไฟล์ประมาณเท่าไหร่** ❌

- **คำตอบ:** ภาพนิ่ง JPEG 1 ภาพต่อเหตุ (snapshot ของ Frigate) ไม่ส่งคลิป **ขนาดยังไม่ได้วัดจากกล้องบนเกาะ**

**8. ภาพและคลิปเก็บฝั่งใคร** ✅

- **คำตอบ:** ฝั่ง Sentiara (เครื่องหน้างาน) ส่งมาแค่ลิงก์อายุ 24 ชม. ลิงก์ลงลายเซ็นด้วย secret อีกตัว แก้ id หรือวันหมดอายุในลิงก์ = 404 อายุนับจากเวลาเกิดเหตุ ส่งซ้ำกี่รอบลิงก์ไม่ยืดอายุ **ไม่มีอะไรเข้า Durable Object ของ ChivarGo**
- 🔴 **ยังใช้จริงไม่ได้:** ลิงก์ต้องเปิดได้จากข้างนอก แต่เครื่องเขาไม่มีระบบล็อกอิน และ **ตัวกลาง (proxy) ที่จะเปิดเฉพาะเส้นหลักฐานยังไม่ได้สร้าง** ระหว่างนี้ถ้าไม่ตั้ง base = ส่งเหตุได้แต่ช่อง `evidence` ว่าง

**9. คลิปก่อนหลังเหตุตามที่เอกสารข้อ 4 ขั้นที่ 2 ระบุไว้ ยาวกี่วินาที** ✅

- **คำตอบ:** วันนี้ไม่ส่งคลิป Frigate บันทึกคลิปเหตุได้ (ใช้อยู่ที่ไซต์ Cora) แต่ยังไม่ได้ต่อเข้าสะพาน ถ้าต้องการ เพิ่มเป็น evidence ชนิด `clip` ได้ด้วยกลไกลิงก์เดิม

**10. Sentiara เก็บภาพและคลิปไว้นานแค่ไหนก่อนลบ** ⚠️

- **คำตอบ:** ขึ้นกับ retention ของ Frigate ที่ไซต์นั้น ที่ Cora วันนี้: snapshot 4 วัน · clip 3 วัน **ของเกาะยังไม่กำหนด** ภาพถูกลบแล้วลิงก์ตอบ 410 "ถูกลบตามระยะเก็บแล้ว" ไม่ส่งภาพแทนที่ผิด

**11. ประมาณการจำนวนเหตุต่อกล้องต่อวันเท่าไหร่** ❌

- หมายเหตุเดิม: ข้อ 7 × ข้อ 11 × จำนวนกล้อง คือพื้นที่ที่ต้องเตรียม
- **คำตอบ:** **ยังไม่มีตัวเลขของเกาะ** ตัวเลขอ้างอิงจากไซต์ Cora ซึ่งคนละสภาพ: 675 จาก 1,000 event เป็นรถ · กล้องทางเข้าตัวเดียวคิดเป็น 41% ของทั้งไซต์ ตัวรวมเหตุ 10 นาทีลดปริมาณลงมาก แต่ตัวเลขจริงต้องวัดหลังติดกล้อง

## หมวด 3 ความสามารถ AI ที่ยืนยันได้จริง

**12. จาก 12 ฟังก์ชันนั้น อันไหนมีโมเดลพร้อมใช้วันนี้ อันไหนต้องเทรนใหม่ อันไหนยังไม่มี** ⚠️

- **คำตอบ:** 5 ข้อใช้ได้วันนี้ · 5 ข้อประกอบได้ · 2 ข้อไม่ควรสร้าง สะพานรับ kind ได้ 8 ชนิด แต่ **ที่แมปจาก Frigate ได้ตรงตัววันนี้มีแค่ label ของวัตถุ** (คน / รถ / จักรยานยนต์) ขยะล้น · ควัน · คนล้ม มีตัวตรวจในระบบแต่ยังไม่ได้ต่อเข้าสะพาน

**13. มีผลทดสอบในสภาพจริงไหม — กลางคืน ฝนตก มุมกล้องสูง คนหรือของบดบัง ขอเป็นตัวเลข** ❌

- **คำตอบ:** ไม่มีของเกาะ และ **กลางคืน / ฝน / มุมสูง ยังไม่เคยวัด**

**14. ส่งค่าความมั่นใจ (confidence) มากับเหตุไหม และฝั่ง ChivarGo ตั้งเกณฑ์ตัดเองได้ไหม** ⚠️

- **คำตอบ:** ส่ง (`confidence` = score ของ Frigate 0–1) ฝั่ง ChivarGo ตั้งเกณฑ์ตัดเองได้
- ⚠️ เขาระบุเองว่า **ค่านี้ไม่ได้สอบเทียบ** 0.8 ไม่ได้แปลว่าถูก 80% ใช้จัดลำดับได้ ใช้เป็นความน่าจะเป็นไม่ได้

**15. อ่านป้ายทะเบียนได้จริงแค่ไหน และกรณีไหนที่อ่านไม่ได้** ✅

- **คำตอบ:** ไม่มีความสามารถนี้ และสะพานปฏิเสธ kind นี้ในโค้ด ใส่ในทะเบียนกล้องก็ถูกตัดทิ้งพร้อมแจ้งใน log มีเทสคุม

**16. อัตราแจ้งผิดประมาณเท่าไหร่** ⚠️

- หมายเหตุเดิม: ถ้าสูงเกิน เจ้าหน้าที่จะเลิกเชื่อการแจ้งเตือนภายในสองสัปดาห์ และระบบจะตายเงียบ
- **คำตอบ:** ตัวเลขวัดจริงตัวเดียวคือ **62% (18/29)** จากบ้านทดสอบ ไม่ใช่จากเกาะ และกลุ่มตัวอย่างเล็ก ทางกลับในข้อ 6 คือเครื่องมือวัดตัวเลขนี้ที่เกาะ — `/v1/incidents/status` นับ `by_outcome` จากผลที่คนกดจริง
- 🔴 **ตัวเลขนี้คือข้อค้นพบที่สำคัญที่สุดของทั้งชุด** ดูผลกระทบข้อ 5 ท้ายเอกสาร

## หมวด 4 ของจริงบนเกาะสีชัง

**17. ตอนนี้มีกล้องกี่ตัวบนเกาะ ของหน่วยงานไหนบ้าง และตัวไหนเชื่อมต่อได้แล้วจริง** ❌

- **คำตอบ:** **ยังไม่มีใครสำรวจ**

**18. กล้องที่มีอยู่เดิมใช้ได้เลยหรือต้องเปลี่ยนเครื่อง** ⚠️

- **คำตอบ:** ที่ไซต์ Cora ใช้กล้องเดิม (Dahua ผ่าน RTSP) ได้โดยไม่เปลี่ยนเครื่อง และทดสอบดึงภาพจาก NVR Hikvision ได้แล้ว → กล้องที่ส่ง RTSP ได้น่าจะใช้ได้ **ต้องยืนยันหน้างาน**

**19. ประมวลผลที่กล้อง ที่ศูนย์กลาง หรือผสม — ถ้าที่ศูนย์กลางต้องใช้แบนด์วิดท์เท่าไหร่ต่อกล้อง** ✅

- **คำตอบ:** ประมวลผลที่หน้างาน วิดีโอไม่ออกจากเครื่อง ขาออกมีแค่ JSON ไม่กี่ KB ต่อเหตุ บวกภาพตอนมีคนเปิดลิงก์

**20. เน็ตบนเกาะหลุด ระบบทำอะไร — เก็บคิวไว้แล้วส่งตามหรือทิ้ง** ✅

- **คำตอบ:** เก็บคิวแล้วส่งตาม (กลไกข้อ 4) กล้องและการตรวจจับทำงานต่อเพราะอยู่ในเครื่อง เกิน 24 ชม. หมดอายุพร้อมบันทึก เขาทดสอบแล้ว: ปิดตัวรับ → ลงคิวได้ → retry แทนที่จะหาย

## หมวด 5 สิทธิ์ ข้อมูล และกฎหมาย

> ทั้งหมวดนี้ฝั่งโค้ดตอบไม่ได้ ต้องให้ผู้บริหารและเจ้าของกล้องตอบ

**21. ใครเป็นเจ้าของภาพ และใครมีอำนาจอนุญาตให้ส่งภาพต่อให้ ChivarGo** ❌

- **คำตอบ:** ยังไม่มีคำตอบ สิ่งที่โค้ดรองรับได้: ภาพอยู่กับเจ้าของกล้อง ไม่ถูกคัดลอกไปไว้ที่อื่น และกล้องที่ไม่มีชื่อในทะเบียน (`data/incident_cameras.json`) ส่งอะไรออกไม่ได้เลย — ทะเบียนนี้คือรายการ "ใครอนุญาตแล้ว"

## สิ่งที่ ChivarGo มีอยู่แล้ว — Sentiara ไม่ต้องสร้าง

- **วงจรจัดการเหตุตามเอกสารข้อ 4** มีอยู่แล้วเกือบครบใน `apps/api/src/sos-service.ts`, `escalation-service.ts` และ `sla-service.ts` ตาราง `sos_alerts`, `sos_dispatch`, `sos_escalations`, `sos_positions` มีอยู่ พร้อมบันไดเร่งที่ยิงตามเวลาจริง (2 นาที แล้ว on-call webhook แล้ว 10 นาที) และ sweep ที่จับงานค้างเกิน SLA
- **การนับความหนาแน่นต่อสถานที่ต่อชั่วโมง** จาก check-in ที่ผ่าน geofence อยู่ใน `apps/api/src/crowd-service.ts` ฟังก์ชัน `checkinsLastHour` ตรงกับเอกสารข้อ 3.7 และทำ pilot ได้ทันทีโดยไม่ต้องมีกล้องสักตัว — ข้อ 17 ตอบว่ายังไม่มีใครสำรวจกล้อง ข้อนี้จึงเป็นงานที่เดินได้วันนี้
- **geofence สำหรับตรวจการเข้าเขต** อยู่ใน `apps/api/src/fence.ts` ตรงกับเอกสารข้อ 3.8
- **ระบบหลักฐานและ audit** อยู่ใน `proofs`, `proof_files`, `evidence-service.ts`, `statements` และ `admin_audit_log` ตรงกับเอกสารข้อ 8
- **แผนที่ ร้านค้า เควส แต้ม รางวัล และการแจ้งเตือนแบบ push** มีครบแล้ว ตรงกับเอกสารข้อ 6
- **สัญญา 409 สำหรับงานที่ส่งซ้ำ** มีอยู่แล้ว — `IdempotencyConflict` ถูกแมปเป็น HTTP 409 ใน `apps/api/src/http.ts` ตรงกับที่ Sentiara ถือว่า 409 คือ "ส่งแล้ว" ไม่ต้องลองซ้ำ
- **การส่ง webhook ออกข้างนอก** มีอยู่แล้วใน `apps/api/src/push/webhook.ts` (`OncallTransport`) ใช้เป็นต้นแบบของการยิง outcome กลับไปหา Sentiara ได้

## ช่องว่างฝั่ง ChivarGo ที่ต้องสร้างใหม่

- **ช่องรับข้อมูลเข้าจากระบบภายนอก** ตอนนี้ไม่มีเลย — ตอนนี้รู้แล้วว่าต้องรับอะไร (payload ข้อ 2) และต้องตรวจอะไร (ลายเซ็นข้อ 3)
- **credential สำหรับระบบคุยกับระบบ** ต้องถือ shared secret สองทาง: ตัวที่ใช้ตรวจของที่เข้ามา และตัวที่ใช้เซ็น outcome ที่ส่งกลับ
- **บทบาทเจ้าของกล้องและเจ้าหน้าที่ภาคสนาม** ตอนนี้มีแค่ admin, moderator, host, operator ส่วน `organisations` ที่มีอยู่ใช้เรื่องสปอนเซอร์ ไม่ใช่การมอบหมายงานตามพื้นที่
- **ตารางส่งต่องานตามพื้นที่ × ประเภทเหตุ × ความเร่งด่วน** ตามเอกสารข้อ 4 ขั้นที่ 4 ซึ่งยังไม่มีอะไรรองรับใน schema — **ยังเขียนไม่ได้เพราะข้อ 22 ยังไม่มีคำตอบ** ไม่รู้ว่าปลายทางคือใคร

## ผลกระทบต่อการออกแบบ — ประเมิน 18 พฤศจิกายน 2569

**1. เหตุจากกล้องใช้ตาราง `sos_alerts` ไม่ได้ ต้องมีตารางของตัวเอง**

`sos_alerts.user_id` เป็น `TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE` (`apps/api/src/db.ts:255`) เหตุจากกล้องไม่มีผู้ใช้เป็นเจ้าของ ทางเลือกคือสร้างผู้ใช้ปลอมสำหรับระบบ ซึ่งจะทำให้ตัวเลขทุกตัวที่นับจาก `sos_alerts` เพี้ยน หรือสร้างตารางใหม่แยก แล้วค่อยต่อเข้าวงจร dispatch / escalation ที่มีอยู่ **ข้อเสนอ: ตารางใหม่** `incidentId` ของ Sentiara ใช้เป็น primary key ได้ตรง ๆ ซึ่งทำให้ได้คุณสมบัติกันซ้ำตามข้อ 5 ฟรีจากตัว schema เอง

**2. สัญญาฝั่งรับชัดพอจะเขียนได้แล้ว**

ต้องการ: route รับ POST หนึ่งเส้น · ตัวตรวจ HMAC-SHA256 ที่เทียบแบบ constant-time และปฏิเสธ timestamp ที่ห่างเกิน 5 นาที · ตอบ 409 เมื่อมี `incidentId` นั้นแล้ว · ตอบ 2xx เร็ว เพราะคิวฝั่งเขาถือเป็น "ส่งแล้ว" จาก 2xx กับ 409 เท่านั้น

> สร้างแล้ว 18 พฤศจิกายน 2569 ดูหัวข้อ "ฝั่งรับของ ChivarGo" ท้ายเอกสาร ตัวตรวจลายเซ็นใช้ `node:crypto` (`createHmac`) เหมือน service อื่นในโปรเจค ซึ่ง `nodejs_compat` รองรับบน Workers อยู่แล้ว ไม่ต้องใช้ WebCrypto

**3. ภาพ: เก็บแค่ลิงก์ แต่ต้องออกแบบหน้าจอรับความจริงว่าภาพอาจไม่มี**

เงื่อนไข ข. ได้ตามต้องการ และเฟสแรกไม่ต้องใช้ R2 เลย เก็บแค่ `ref` กับ `expiresAt` แต่มีสามสถานะที่หน้าจอต้องแสดงต่างกันจริง ๆ ไม่ใช่ช่องภาพว่าง ๆ: **ยังไม่มีหลักฐาน** (proxy ฝั่งเขายังไม่ได้สร้าง ข้อ 8) · **ลิงก์หมดอายุแล้ว** (24 ชม.) · **ภาพถูกลบตามระยะเก็บ** (410) นี่คือเงื่อนไข ก. ในรูปของภาพ ถ้าเก็บแค่ URL แล้วปล่อยให้หน้าจอโชว์รูปแตก เท่ากับบอกผู้ใช้ว่ามีหลักฐานทั้งที่ไม่มี

**4. ยังไม่มีอะไรมาถึงจริง การทดสอบแรกต้องเป็น `kind=test`**

เขาระบุเองว่ายังไม่ได้ deploy ขึ้นเครื่องจริง ยังไม่เคยยิงมาที่ ChivarGo ตัวจริง และตัวกลางสำหรับลิงก์หลักฐานยังไม่ได้สร้าง แปลว่าถ้าเราสร้างฝั่งรับเสร็จ สิ่งที่พิสูจน์ได้อย่างแรกคือเหตุชนิด `test` ที่มาพร้อมช่อง `evidence` ว่าง ไม่ใช่เหตุจริงที่มีภาพ ควรรับที่ staging ก่อน ไม่ใช่ที่ chivargo.com

**5. 62% แจ้งผิด หมายความว่าห้ามส่งต่อหน่วยงานโดยอัตโนมัติ เด็ดขาด**

ตัวเลขเดียวที่วัดจริงคือ 18 จาก 29 เป็นการแจ้งผิด (จากบ้านทดสอบ กลุ่มตัวอย่างเล็ก ไม่ใช่เกาะ) และ `confidence` ไม่ได้สอบเทียบ จึงใช้ตั้งเกณฑ์ตัดอัตโนมัติไม่ได้ ถ้าต่อตรงเข้าบันไดเร่งของ `escalation-service.ts` เจ้าหน้าที่จะได้สายจากการแจ้งผิดมากกว่าเหตุจริง และจะเลิกเชื่อภายในสองสัปดาห์ตามที่คำถามข้อ 16 เตือนไว้ **เฟสแรกต้องเป็นคิวที่คนกดยืนยันก่อน** เหตุที่ยังไม่มีคนดูต้องไม่นับเป็นเหตุที่ส่งแล้ว — ตรงตามเงื่อนไข ก. การกดยืนยันนั้นเองคือข้อมูลที่ส่งกลับทาง `/v1/incidents/outcome` และเป็นทางเดียวที่จะได้ตัวเลขแจ้งผิดจริงของเกาะ

**6. ต้องรวมเหตุอีกชั้นฝั่งเรา**

`incidentId` กันซ้ำได้ในหน้าต่าง 10 นาที แต่เขาเตือนเองว่าเหตุที่ค้างข้ามรอยต่อจะได้ id ใหม่ ฝั่งเราต้องรวมด้วย กล้อง + kind + ช่วงเวลา อีกชั้น ไม่งั้นรถจอดกีดขวางคันเดียวจะกลายเป็นงานใหม่ทุก 10 นาทีในคิวของเจ้าหน้าที่

**7. ขอบเขตที่แคบกว่าเอกสารแนวคิดมาก**

เอกสารแนวคิดลิสต์ 12 ฟังก์ชัน แต่ที่ส่งมาได้จริงวันนี้คือ label ของวัตถุจาก Frigate (คน / รถ / จักรยานยนต์) ขยะล้น ควัน คนล้ม มีตัวตรวจแต่ยังไม่ได้ต่อ ไม่มีการอ่านป้ายทะเบียน ไม่มีคลิป ไม่มีคำบรรยายจาก VLM การคุยกับหน่วยงานควรพูดจากขอบเขตนี้ ไม่ใช่จาก 12 ฟังก์ชัน

**8. สิ่งที่ยังประเมินไม่ได้**

ขนาดไฟล์ (ข้อ 7) และจำนวนเหตุต่อกล้องต่อวัน (ข้อ 11) ยังไม่มีตัวเลขของเกาะ จึงยังคิดต้นทุนไม่ได้ แต่ความเร่งด่วนลดลงมาก เพราะภาพไม่เข้าฐานข้อมูลเรา ตัวเลขที่ขาดกระทบ "คิวของเจ้าหน้าที่จะล้นไหม" มากกว่า "พื้นที่จะเต็มไหม"

## ฝั่งรับของ ChivarGo — สร้างแล้ว 18 พฤศจิกายน 2569

ยังไม่ได้ deploy และยังไม่ได้ตั้ง secret ที่ไหน ต้องส่งข้อมูลชุดนี้ให้ Sentiara ตั้งค่า

**ปลายทางที่ Sentiara ต้องตั้งใน `CHIVARGO_INCIDENT_URL`**

```
POST https://<host>/integrations/sentiara/incident
X-Sentiara-Timestamp: <unix วินาที>
X-Sentiara-Signature: sha256=<hex ของ HMAC(secret, "<timestamp>." + body ดิบ)>
Idempotency-Key:      <incidentId>
```

**รหัสสถานะที่ตอบกลับ** ตรงกับที่คิวของเขาตีความ (คำตอบข้อ 4)

| รหัส | ความหมาย | ฝั่งเขาทำอะไร |
|---|---|---|
| `200` | รับแล้ว เข้าคิวรอคนดู | ถือว่าส่งแล้ว |
| `409` | มี `incidentId` นี้อยู่แล้ว | ถือว่าส่งแล้ว เลิกลองซ้ำ |
| `401` | ลายเซ็นไม่ผ่าน timestamp เกิน 5 นาที หรือ body ถูกแก้หลังเซ็น | ไม่ลองซ้ำ |
| `422` | ประเภทเหตุที่ ChivarGo ไม่รับ (ป้ายทะเบียน) | ไม่ลองซ้ำ |
| `400` | body ไม่ใช่ JSON หรือฟิลด์ไม่ครบ | ไม่ลองซ้ำ |
| `404` | ปลายทางนี้ยังไม่ได้ตั้ง secret | ไม่ลองซ้ำ — อย่าเปิดตัวส่งก่อนได้ secret |

คำตอบ 200 มีรูปแบบ `{ incidentId, mergedInto, reviewState: "unreviewed", evidence: "none" | "available" | "expired" }` — `reviewState` บอกตรง ๆ ว่ายังไม่มีใครดู ไม่มีการส่งต่อหน่วยงานใด ๆ เกิดขึ้นจากการรับ

**ตัวแปรที่ฝั่ง ChivarGo ต้องตั้ง**

```
CHIVAGO_SENTIARA_SECRET=<สุ่ม ≥ 24 ตัว — ค่าเดียวกับ CHIVARGO_SHARED_SECRET ฝั่งเขา>
CHIVAGO_SENTIARA_OUTCOME_URL=https://<proxy ของเขา>/v1/incidents/outcome
CHIVAGO_SENTIARA_MERGE_SEC=1800   # ไม่ตั้งก็ได้ ค่าเริ่มต้น 30 นาที
```

ถ้า `CHIVAGO_SENTIARA_SECRET` ยังไม่ตั้ง หรือสั้นกว่า 24 ตัว เส้นนี้ตอบ 404 เหมือนพาธที่ไม่มีอยู่ ไม่ประกาศตัวว่ามีเส้นนี้แต่ปิดอยู่ ซึ่งสมมาตรกับฝั่งเขาที่ตัวส่งปิดเป็นค่าเริ่มต้น

**ไฟล์ที่เพิ่ม**

- `apps/api/src/incident-signature.ts` — ตรวจและสร้างลายเซ็น ใช้ `node:crypto` เทียบแบบ constant-time ด้วย `constantTimeEqual` จาก `scrypt.ts` ปฏิเสธ timestamp ที่ห่างเกิน 5 นาที
- `apps/api/src/camera-incident-service.ts` — รับเหตุ ตรวจ payload รวมเหตุชั้นที่สอง คิวรอคนดู บันทึกผลตัดสิน และยิง outcome กลับ
- ตาราง `camera_incidents` กับ `camera_incident_evidence` ใน `apps/api/src/db.ts` (`SCHEMA_VERSION` ขยับ 7 → 8)
- `POST /integrations/sentiara/incident` ใน `apps/api/src/server.ts` วางนอก middleware ของผู้ใช้ทั่วไป
- เทส 53 ข้อใน `incident-signature.test.ts`, `camera-incident-service.test.ts`, `camera-incident-routes.test.ts`

**การตัดสินใจที่ฝังอยู่ในโค้ด**

- **ไม่มีการส่งต่อหน่วยงานอัตโนมัติ** เหตุที่เข้ามาอยู่สถานะ `unreviewed` และไม่แตะ `escalation-service.ts` เลย เพราะอัตราแจ้งผิด 62% กับ confidence ที่ไม่สอบเทียบ (คำตอบ 14 และ 16)
- **แยกตารางจาก `sos_alerts`** เพราะ `user_id` เป็น `NOT NULL REFERENCES users(id)` การใส่ user ปลอมจะทำให้ตัวเลขทุกตัวที่นับจาก SOS เพี้ยน
- **`review_state` กับ `outcome_sent_at` เป็นสองฟิลด์** ผลตัดสินของคน กับ การแจ้งผลกลับที่สำเร็จจริง เป็นข้อเท็จจริงสองอย่าง — เงื่อนไข ก.
- **`verified: true` ที่ส่งมาจากฝั่งเขาถูกทิ้ง** ระบบผู้ส่งอ้างว่าคนยืนยันแล้วไม่ได้ การยืนยันเกิดที่นี่หรือไม่เกิดเลย
- **ป้ายทะเบียนถูกปฏิเสธในโค้ด** ด้วย regex ที่จับการเปลี่ยนชื่อ (`plate`, `licence`, `anpr`, `lpr`) เป็นการปฏิเสธชั้นที่สองซ้อนกับฝั่งเขา
- **ไม่เก็บไบต์ของภาพ** เก็บแค่ลิงก์กับ `expires_at` และแยกสถานะ `none` / `available` / `expired` ให้หน้าจอพูดความจริงได้สามแบบ
- **รวมเหตุชั้นที่สอง** นับจากรายงานล่าสุดของกล้องนั้น ไม่ใช่จากงานแรก รถที่จอดค้างสองชั่วโมงจึงเป็นงานเดียว ไม่ใช่งานใหม่ทุก 30 นาที

**ที่ยังไม่ได้ทำ**

- **หน้าจอในคอนโซลให้เจ้าหน้าที่กดยืนยัน** ชั้นข้อมูลพร้อมแล้ว (`pendingIncidents`, `reviewIncident`, `incidentCounts`) แต่ยังไม่มีหน้าจอ ผมไม่เดา auth ของคอนโซล ต้นแบบที่ควรลอกคือ `apps/api/src/console/sos-desk.ts`
- **sweep ที่ยิง outcome ซ้ำอัตโนมัติ** `sendPendingOutcomes` เขียนแล้วและเทสแล้ว แต่ยังไม่ได้ลงทะเบียนใน `sweeps.ts`
- **ยังไม่เคยยิงจาก Sentiara ตัวจริง** เพราะฝั่งเขายังไม่ได้ deploy ที่พิสูจน์แล้วคือ `kind=test` ผ่าน `app.request()` ในเทส
