## How this was run, and why it was split

Write paths were exercised against a **local server on a throwaway database**,
seeded fresh from `seed-db.ts`. They were deliberately NOT pointed at
production, because on the live pilot:

- a check-in writes to the ledger an auditor is asked to trust;
- `autoApprove` is on, so a posted story reaches a public screen with no human
  in between;
- the badminton booking site behind the court feed takes real payments.

A UAT that leaves test rows in any of those is worse than no UAT. So:

| Surface | How it was tested |
|---|---|
| Write paths (register, check in, post, redeem) | Local server, fresh DB, port 8799 |
| Read paths, availability, auth boundaries | **Live**, read-only, against chivargo.com |
| Third-party feeds | **Live**, read-only |
| Regression | Full automated suites in the repo |

Runner: `scratchpad/uat/run-uat.mjs` (36 checks). Live probes were run
separately, read-only (14 checks).

### The two checks that failed first, and why they were my error

Both were defects in the **test**, not the product. Recording them so nobody
re-raises them:

1. **"an unregistered device is refused" — got 200.** Correct behaviour.
   `openIdentityAllowed()` keeps identity open while *no device has ever
   registered* and closes it the instant the first one does (documented in
   `http.ts`). The UAT hit `/profile` as its very first call on an empty
   database. The check now asserts the real property: open before the first
   registration, **401 after it** — and that passes.

2. **"the host console is not open to a traveller" — console answered.**
   `/console` is in `PUBLIC_PREFIXES` on purpose: a host cannot sign in to a
   page that requires being signed in. The check now tests the thing that
   matters — `/console/`, `/console/pending`, `/console/history` with no
   session — and all three refuse. Live, `/console/pending` answers **303** to
   the login page.

### Check-in, exercised against the real geofence

are real distance checks:

## Findings

### F1 — the Swift CI job times out (infrastructure)

On `chore/close-the-geofence`, `typescript` (4 min) and `dart` (27 s) passed
while `swift` ran **15 minutes and was cancelled**, which marks the whole `ci`
run failed and leaves the PR `UNSTABLE`. The change under test is one line of
`fly.toml` and cannot touch the Swift SDK, so this is a runner timeout, not a
regression. Re-run queued.

Worth watching: if it recurs, the Swift job needs a longer timeout or a cache,
because it currently blocks merges for changes it has nothing to do with.

### F2 — 24–29 October rows are not presence evidence

Not a defect: the geofence was open on request from 24 to 29 October, so every
check-in, quest arrival and story in that window passed no distance, accuracy,
mock-location or travel check. The app said so throughout (the red band was
up), so nobody was misled while it was on.

The gap is afterwards: **the rows carry no mark of their own.** Anyone auditing
this database later cannot tell which rows came from the open window. PR #163
closes the fence and records the dates in `fly.toml` so the window is at least
written down somewhere.

If those rows ever need to be separated programmatically, that needs a column,
not a comment — worth deciding before the next time the switch is thrown.

## Not covered

Stated plainly so the number above is not read as more than it is:

- **Native app UI** — the mobile suites render screens, but no iOS/Android
  build was driven by hand.
- **Payment flows** — the booking site's checkout was not exercised; it takes
  real money.
- **Story posting and host approval end to end** — posting reaches a public
  screen under `autoApprove`, so it was not driven on production, and the
  local run checked the read side only.
- **Load and concurrency** — single-user journeys only.
- **The console's authenticated pages** — refusal without a session was
  verified; the signed-in host journey was not driven.
